## 1. Toyota SecOC cars (RAV4 Prime, Sienna): how SecOC is handled, is longitudinal supported, what limits it

### Takeaway
Toyota SecOC is the only other port that signs actuator frames, and it does it entirely in userspace with a recovered key, with the stock camera's frames **always** blocked by the panda (static relay block), so there is no handover and no counter alignment problem to solve. Longitudinal exists in code (accel moved to a second, signed frame 0x183) but the whole SecOC path is debug-build-only in panda and dashcam-only in release.

### Cited Findings
- **[code]** The MAC is built in Python: freshness = trip counter (16 bit) + reset counter (20 bit) + message counter (8 bit) + reset flag; AES-CMAC truncated to 28 bits over `[addr][4 payload bytes][freshness]`; the wire frame carries payload + 2-bit message-counter flag + 2-bit reset flag + MAC — [secoc.py:7-34](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/secoc.py)
- **[code]** The car controller keeps one message counter per signed frame (LKA, LTA, ACC), starting at 0 and **reset to 0 whenever the car's `SECOC_SYNCHRONIZATION.RESET_CNT` changes**; it also verifies the sync message MAC and logs "wrong key?" on mismatch. Counters are not seeded from the stock camera's stream — [toyota/carcontroller.py:79-82, 98-108](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/toyota/carcontroller.py)
- **[code]** Longitudinal on SecOC cars: the normal `ACC_CONTROL` (0x343) is still sent but with accel forced to 0, and the real accel goes in `ACC_CONTROL_2` (0x183), which is MAC-stamped with its own counter — [toyota/carcontroller.py:271-282](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/toyota/carcontroller.py); builder at [toyotacan.py:59-63](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/toyota/toyotacan.py)
- **[code]** Panda: SecOC long TX list adds 0x183 and 0x343, both `check_relay = true` (so the camera's copies from bus 2 are statically blocked and their appearance on bus 0 is a relay malfunction) — [toyota.h:14-17, 34-37](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/safety/modes/toyota.h). On SecOC, 0x343 may only carry the inactive accel; 0x183 gets the normal `longitudinal_accel_checks` (+2.0 / -3.5 m/s²) — [toyota.h:261-293](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/safety/modes/toyota.h)
- **[code]** Panda does not verify or generate MACs. It only range-checks the plain accel field in the signed frame. SecOC cars use different RX messages for driver inputs: cruise from 0x176, gas from 0x116 `GAS_PEDAL_USER`, brake from 0x101 — [toyota.h:150-160](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/safety/modes/toyota.h)
- **[code]** The panda SecOC flag is only read under `#ifdef ALLOW_DEBUG` — [toyota.h:436-439](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/safety/modes/toyota.h). The car port sets `secOcRequired = True` and `dashcamOnly = is_release` — [toyota/interface.py:35-38](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/toyota/interface.py)
- **[code]** SecOC platforms are flagged `TSS2 | NO_STOP_TIMER | NO_DSU | SECOC` (camera-based ACC, not radar-ACC), so `openpilotLongitudinalControl` is true by the normal TSS2 rule and no radar disable is involved — [toyota/values.py:118-124](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/toyota/values.py), [toyota/interface.py:106-109](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/toyota/interface.py). The docs footnote for these cars points at "secoc-cars-with-recoverable-keys" — [toyota/values.py:102](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/toyota/values.py)
- **[code]** The gas interceptor is force-disabled on SecOC cars — [toyota.h:449-452](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/safety/modes/toyota.h)
- **[code]** Tests: `test_toyota.py` has SecOC safety classes; SecOC relay-malfunction/blacklist addresses include 0x131, and a dedicated test asserts no actuation is sent in `ACC_CONTROL` on SecOC cars (accel must be in `ACC_CONTROL_2`) — [test_toyota.py:17, 432-434, 477-504](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/safety/tests/test_toyota.py)
- **[PR]** Upstream "Toyota: Add SECOC longitudinal control" merged 2025-09-29; body: adds a counter for SecOC ACC messages, a new ACC message for the second `ACCEL_CMD`, removes the SecOC `openpilotLongitudinalControl` disable, and creates a SecOC variant of the long TX list with 0x183 — [commaai/opendbc#1385](https://github.com/commaai/opendbc/pull/1385)
- **[PR]** "Toyota SecOC platforms should use torque control", merged 2026-01-29, body: "Plus they're dashcam only" — [commaai/opendbc#3086](https://github.com/commaai/opendbc/pull/3086)

### Inferences
- Toyota's design avoids the handover problem rather than solving it: because 0x343/0x183/0x2E4/0x131 are always blocked from the camera side, the receiver only ever sees openpilot's counter stream, so a free-running counter that restarts at 0 on each reset-counter change is sufficient. Fisker's 0x121 is different because the port deliberately lets the OEM frame through when openpilot is not sending (time-based relay), which is what creates the alignment requirement.
- The Toyota pattern "keep the legacy frame alive with inactive values and put the real request in the signed frame" is close to Fisker's 0x117/0x118 (plain status) + 0x121 (signed accel) split. Toyota's panda enforces that the unsigned frame cannot actuate; the Fisker panda already does the equivalent for 0x117/0x118 (see section 8).
- Nothing in the Toyota port substitutes a signed frame in the forward path. Fisker's `fwd_modify` candidate substitution is unique to this checkout (the hook was introduced by local commit `2b4fbd21`, "fisker: race-free SecOC handover via panda candidate substitution").

### Gaps
- I did not find a public write-up of on-road results for Toyota SecOC longitudinal (fault behaviour, counter resync behaviour at reset boundaries). The web search surfaced only community key-extraction docs with conflicting model-year claims; I did not use them.
- Whether the Toyota PCM tolerates the message counter jumping back to 0 mid-window on engage is not documented; in Toyota's case the question does not arise because the stock stream never reaches the PCM.

## 2. How each port blocks the OEM accel/status frames and guarantees one sender

### Takeaway
The standard mechanism is static: any TX message marked `check_relay` is (a) always blocked in the forward path from the stock module's bus and (b) a relay-malfunction trigger if it is seen on the destination bus, which then blocks all TX and all forwarding. Only Tesla (AEB/LKAS/autopark passthrough), Honda Nidec (AEB brake passthrough) and the local Fisker port opt out with `disable_static_blocking` and decide dynamically; no upstream port blocks on `controls_allowed`, and none uses a time-since-last-TX relay except Fisker.

### Cited Findings

Common mechanism
- **[code]** `CanMsg.check_relay`: "trigger relay malfunction if existence on destination bus and block forwarding to destination bus"; `disable_static_blocking`: "static blocking is disabled so safety mode can dynamically handle it (e.g. selective AEB pass-through)" — [declarations.h:88-94](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/safety/declarations.h)
- **[code]** Forward path: blocked if `relay_malfunction` or `disable_forwarding`; else blocked if the address is a `check_relay` TX message for the destination bus (unless `disable_static_blocking`); else the mode's `fwd` hook decides — [safety.h:268-289](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/safety/safety.h)
- **[code]** Stock-ECU detection: every received message is compared against all `check_relay` TX entries; a match on the TX bus (after a 1 s grace after mode set) latches `relay_malfunction` — [safety.h:209-218, 390-399](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/safety/safety.h). With `relay_malfunction` set, `safety_tx_hook` returns false for everything — [safety.h:242-254](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/safety/safety.h)
- **[PR]** This config-driven design landed upstream in March-April 2025: "safety: relay malfunction config" ([#1959](https://github.com/commaai/opendbc/pull/1959)), "safety: block messages with static config" ([#2092](https://github.com/commaai/opendbc/pull/2092)), and a bug it exposed: "If we're sending SCC messages on bus 0, we should always check for relay malfunction. Previously camera SCC long safety didn't check for this" ([#2094](https://github.com/commaai/opendbc/pull/2094))

### Inferences
- Every upstream port that keeps the stock module on the bus makes the mode switch at **safety-mode init**, not at engage: once the long flag is set the stock accel frame is never forwarded again (Tesla's AEB exception aside), and openpilot must therefore transmit continuously, engaged or not, with inactive values. This is why none of them needs counter alignment at engage/disengage.
- Fisker is the only port where the receiver sees two alternating senders of the same accel frame during a drive. That is a design choice with a cost the other ports do not pay: counter/SecOC continuity at every transition, and a window (the relay timeout) in which the OEM frame is still blocked after openpilot stops.
- If the Fisker ADAS module's 0x121/0x117/0x118 are acceptable to block permanently while the long flag is set (as Tesla/Rivian/Toyota do), the handover problem disappears at the price of openpilot having to send valid "ACC standby" frames for the whole drive and of losing stock ACC as a fallback. Tesla's pattern of a single boolean that simultaneously opens the forward path and closes the TX path (AEB) is the tested precedent for any passthrough exception.
- Tesla keeping the stock `DAS_control` as a counter/checksum-validated RX check while blocking it is the precedent for "panda keeps watching the OEM stream it is replacing".

### Gaps
- No design discussion was found explaining why upstream rejected or never tried `controls_allowed`-based or time-based blocking for accel frames; the conclusion that it is unused is from reading all `fwd` hooks, not from a statement by maintainers.
- The upstream Rivian long PR (#3805) has an empty body; what changed about the "missing set speed" blocker is not documented in the PR text I read.

## 3. Counter / checksum / SecOC continuity at engage and disengage

### Takeaway
Ports use two distinct counter strategies depending on who else is on the bus: a free-running counter when the stock frame is always blocked (the long case everywhere upstream), and "stock counter + 1" or a verbatim copy of the last stock frame when openpilot injects a single frame alongside a live stock stream (cancel/resume). No upstream port aligns a free-running accel counter to the OEM stream, because none hands the accel frame back and forth.

### Cited Findings
- **[code] Free-running when sole sender.** Tesla long: `cntr = (self.frame // 4) % 8` — [tesla/carcontroller.py:52-56](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/tesla/carcontroller.py). Rivian long: `frame % 15` (counter is 0-14, not full 4-bit) with CRC recomputed — [riviancan.py:66-77](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/rivian/riviancan.py). GM: `idx = (self.frame // 4) % 4` — [gm/carcontroller.py:100](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/gm/carcontroller.py). Subaru long frames: `frame // 5` passed to builders that set `COUNTER = frame % 0x10` — [subaru/carcontroller.py:111-120](/Users/hiremanirmss/Fisker/sunnypilot/opendbc_repo/opendbc/car/subaru/carcontroller.py)

### Inferences
- The upstream precedent closest to Fisker's handover is the "stock counter + 1 / only send when the stock counter advanced" family (VW `gra_send_ready`, Tesla cancel). Its rule is: one openpilot frame per observed stock frame, numbered as the stock frame's successor. - No upstream port demonstrates continuity across a mid-drive sender change for an accel frame, so there is no reference for how tolerant a receiver's E2E/SecOC freshness window is to a one-frame gap or duplicate at handover.
- I found no discussion of receivers that latch a fault on a single duplicate counter versus those that debounce; the only quantitative debounce in the codebase is panda's own `MAX_WRONG_COUNTERS` for RX.

## 4. Standstill: stopping, holding, resuming

### Takeaway
There are three models: (1) the car holds itself and resumes on positive accel with no special signal (Tesla, Rivian, TSS2 Toyota), (2) the port sets an explicit stop/hold request while `longControlState == stopping` and a release/drive-off bit when it wants to move (VW MQB/MEB, Honda Bosch, Hyundai `StopReq`, GM full-stop flags), and (3) with stock longitudinal the port spams the resume button when `CC.cruiseControl.resume` is set. The hold request is always derived from `actuators.longControlState`, and VW MEB shows that the **release** sequence, not the hold, is where cars fault.

## 5. What common safety expects for gas, brake, cancel; and what the standard tests require

### Takeaway
Common safety needs each port to set four globals from validated RX messages — `gas_pressed`, `brake_pressed`, `vehicle_moving`, and cruise state via `pcm_cruise_check` (plus `regen_braking` if there is a paddle) — and to call the shared `longitudinal_*_checks` on every actuation field. Gas does not disengage: it only removes longitudinal permission (`get_longitudinal_allowed`), so with gas pressed the port must send the inactive accel value. The standard `CarSafetyTest` + `LongitudinalAccelSafetyTest` classes enforce all of this, and the Fisker tests currently do not inherit from them.

- Candidate mechanisms to test against the drive log, each grounded in how another port avoids the same class of error: (a) the driver's accelerator or one-pedal/creep torque adding to the ACC request while openpilot still sent a lower, non-inactive request — other ports send the inactive value or an explicit override status when gas is pressed (section 5), and Fisker panda does not track gas; (b) jerk/tolerance fields in 0x118 not matching the 0x121 request (Tesla/VW/Hyundai all send jerk limits consistent with the accel command); (c) a step in the request that the powertrain could not follow (Toyota rate-limits and uses predicted-error feedback); (d) a counter/E2E discontinuity at handover making the VCU/ESP hold the previous request for a few frames while the measured accel moved on (section 3).

### Inferences
- Since Fisker's 0x118 carries AEB activation and ESP standstill fields that openpilot must not assert, the Tesla rule set is the closest model for it: parse the OEM's 0x118 on bus 2 as a validated RX check, and when the OEM asserts AEB, forward the OEM frame and reject openpilot's — a state-based exception layered on top of whatever relay rule is used.
- The order in which other ports solved these suggests dependencies: gas tracking and the standard test classes first (they change what panda permits), then counter continuity (it changes what the receiver accepts), then standstill and cancel (they add new requests that panda must gate), with fault-threshold bisection using the longitudinal maneuvers tool once the stream is clean.

### Gaps
- None of the precedents has been validated against Fisker hardware; signal names and behaviours on the Ocean for hold, drive-off, cancel and tolerance fields were not part of this research.
